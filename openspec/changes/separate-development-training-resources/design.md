## Context

当前规划把开发机描述为创建时选择团队、资源队列和卡数的长生命周期工作负载，并通过交互心跳、内核状态、平台任务和`GPU`利用率联合判断是否闲置。这个模型把代码编辑、配置准备等长时间交互会话与稀缺`GPU`资源绑定，只有达到回收阈值后才能释放占用；同时，训练命令行虽然复用`train.yaml`，但没有明确开发机与正式训练是两个独立工作负载。

本次只修订规划，不改变现有系统运行行为。开发机仍需要复用平台现有团队、资源队列、镜像、工作集群和共享存储边界，不能为默认无`GPU`再设计一套独立权限或资源池。

## Goals / Non-Goals

**Goals:**

- 开发机默认使用`CPU`和内存启动，工作负载不申请`GPU`。
- 通过训练命令行（`CLI`）提交正式训练时创建独立训练任务，由任务规格重新确认队列和`GPU`资源。
- 保持开发环境与训练任务的镜像、路径、数据引用和配置可复用、可追溯。
- 分离开发机和训练任务的生命周期、状态与资源计量。
- 让空闲回收只负责通用计算资源和开发环境清理，不再承担主要的`GPU`防空转职责。

**Non-Goals:**

- 不设计运行中开发机动态挂载或卸载`GPU`。
- 不新增开发机专用队列、项目角色、资源授权或`GPU`预留模型。
- 不改变现有训练任务的排队、调度、权限和资源计量语义。
- 不修改生产代码、接口、数据库或测试。

## Decisions

### 开发机工作负载默认不申请 GPU

开发机创建时继续选择现有团队和可用落点，复用既有权限、工作集群、镜像及存储校验；工作负载只声明`CPU`和内存，不声明`nvidia.com/gpu`等`GPU`资源。资源队列如继续参与落点选择，只用于既有权限、数据中心以及`CPU`和内存计量，不检查或占用队列`GPU`额度。

相比“开发机先占卡、闲置后回收”，默认无`GPU`从资源申请源头消除编辑、阅读日志和配置准备期间的空转。相比新增开发机专用资源池，继续复用现有团队和落点关系能够避免新的授权模型与调度抽象。

### GPU 工作通过 CLI 创建独立训练任务

开发机内的`aitrain job validate`、`dry-run`和`submit`继续使用版本化`train.yaml`。执行`submit`时，训练任务管理根据任务规格重新选择或确认团队、资源队列、节点数、每节点卡数及其它资源，完成服务端校验后创建独立训练任务；提交动作不修改开发机资源，也不把开发机原地转换为训练工作负载。

相比给运行中的开发机动态挂卡，独立任务沿用已有训练任务契约、队列准入、调度、日志、取消和审计能力，调用链更短，失败与重试语义也更清楚。需要`GPU`的小规模验证同样提交小规格训练任务，不另建交互式挂卡路径。

### 提交时固化可复现快照

训练任务提交时固化镜像摘要、工作目录与共享路径、外部数据引用、任务配置和资源规格。任务只读取共享持久目录或任务快照中声明的内容，不依赖开发机进程继续运行；提交后开发机中的未保存修改不影响已创建任务。

这一边界保留“开发环境与正式训练一致”的价值，但一致性来自不可变镜像、统一路径和版本化任务规格，而不是复用同一个运行实例。

### 生命周期与资源计量相互独立

开发机的启动、停止、重启和闲置回收只影响自身`CPU`、内存和会话；训练任务从创建后独立排队、运行、停止和计量`GPU`。关闭开发机不得取消已提交任务，结束训练任务也不得关闭开发机。

开发机仍保留基于终端和`JupyterLab`活动的闲置回收，用于释放通用计算资源，但不再使用`GPU`利用率作为判定条件，也不把回收机制描述为避免长期占卡的主要措施。

## Risks / Trade-offs

- [开发机无法直接进行交互式 GPU 调试] → 首期接受该限制，使用小规格训练任务完成需要`GPU`的验证；出现明确高频需求后再单独评估受时限约束的交互式能力。
- [开发机本地修改未进入任务快照会导致训练内容不一致] → `CLI`提交前展示镜像、路径、配置和输入快照，未保存在共享持久目录或未进入任务规格的内容不得作为已提交任务输入。
- [开发机和训练任务分离后用户需要查看两个状态] → `CLI`返回稳定任务标识，并从开发机提供任务详情和日志入口，不合并两者生命周期。
- [通用计算节点暂时不足] → 沿用现有调度失败与重试提示，不回退为申请`GPU`资源启动开发机。

## Migration Plan

1. 修订开发机工作空间的背景、目标、生命周期图和建议方案，删除默认申请卡数及依赖`GPU`利用率回收的描述。
2. 修订训练命令行流程，明确`submit`创建独立训练任务并重新申请`GPU`。
3. 在训练任务管理章节补充开发机来源任务的快照与生命周期边界。
4. 更新规划总览、功能排期、季度路线和行业映射。
5. 扫描开发机长期占卡、创建时申请卡数和动态挂卡等冲突描述，并运行文档与 OpenSpec 验证。

回退时只恢复本变更调整的规划段落，不修改现有运行行为或工作区中的其它变更。
