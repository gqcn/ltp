# AI-HPC云原生架构演进背景及规划

# 背景概述

## 现状与痛点

当前公司 LLMOps 平台采用双技术栈架构：

- **开发训练场景**：基于`Slurm`构建，这是传统 HPC 领域的经典批处理调度系统，擅长处理大规模分布式训练任务，但设计上缺乏云原生的弹性与敏捷性。

- **推理服务场景**：基于`K8S+Volcano`构建，依托云原生容器编排能力，能够高效实现服务化部署与弹性扩缩容，更适配在线推理的动态负载特性。

这种双技术栈并行的架构，在业务高速发展期逐渐暴露出多维度的深层问题：

1. **运维复杂度高**：技术团队需要同时维护两套调度系统，投入额外人力成本进行问题排查与版本迭代，还面临技能栈割裂的挑战，新成员的学习与适配周期显著延长。

2. **资源调度低效**：训练集群与推理集群的资源物理隔离，导致资源无法根据业务负载进行动态调配（如潮汐调度），整体资源利用率偏低。

3. **研发迭代缓慢**：两套系统的功能迭代需要独立规划与开发，新功能无法快速在全场景落地，拉长了业务价值交付周期。

4. **用户体验割裂**：多租户、资源管理、操作审计等公共能力在两套系统中规则不统一，需重复学习适配，易引发误操作，拖累研发与运维效率。

5. **可观测性缺失**：两套独立的资源监控告警体系，各自维护不同的指标采集规则与告警策略，无法形成统一的全局视图。

## 行业最佳实践与架构升级方向

结合云原生技术的行业演进趋势，以及LLMOps平台的规模化落地经验，**统一技术栈为****`K8S+Volcano`****云原生架构**是解决当前痛点的最优路径，其核心价值与实践依据如下：

1. **技术栈统一的效率红利**

    `Volcano`作为CNCF 毕业的云原生批量计算调度引擎，不仅继承了 K8S 的弹性调度与容器化优势，还通过自研的 Gang 调度、队列管理、优先级抢占等能力，完美适配 HPC 场景下大规模分布式训练的资源调度需求。业内头部企业已通过`K8S+Volcano`实现了训练与推理的混部调度，显著降低了运维人力投入，提升了资源使用效率。

2. **资源池化与弹性调度**

    基于 K8S 的全局资源池化能力，可实现训练与推理任务的动态资源调度。通过配置自定义调度策略，能够根据业务潮汐效应灵活分配资源，最大化集群整体利用率。

3. **云原生生态的协同能力**

    统一到 K8S 架构后，可无缝集成云原生生态中的成熟工具链：

    - **存储**：通过 CSI 接口对接分布式存储，实现训练数据的高吞吐共享与推理模型的热加载。

    - **网络**：借助 CNI 插件，实现 Pod 间的高速网络通信，满足分布式训练的低延迟需求。

    - **可观测性**：通过`Prometheus+Grafana`构建统一的监控体系，实现全链路指标采集与告警，提升问题定位效率。

4. **面向未来的业务扩展性**

    随着大模型技术的演进，LLMOps平台需要支持多框架兼容、异构算力调度与联邦学习等复杂场景。`K8S+Volcano`的云原生架构通过插件化设计，能够快速适配新的硬件与框架，无需重构底层调度逻辑，为业务的长期演进提供技术底座。

## 升级核心价值总结

通过将技术栈统一为`K8S+Volcano`，我们将构建一个**高效、弹性、可扩展**的云原生 LLMOps 平台，最终实现：

- **运维降本**：减少跨系统运维投入，提升团队响应速度。

- **提效增益**：提升资源利用率，缩短模型迭代周期。

- **体验优化**：统一的用户操作界面与调度逻辑，降低学习成本与操作失误率。

- **技术前瞻**：基于云原生生态的持续演进能力，支撑长期业务增长。

# 架构设计

## **设计目标**

- 对标业内主流云原生实践，聚焦核心服务能力，兼顾平台易用性、高效性与稳定性，避免功能冗余。

- 作为 MLOps 体系的关键组成，AI 模型开发训练平台与推理服务平台统一整合至 PA 平台，深度复用多租户管理、资源权限、操作审计、计费策略等公共能力，降低架构复杂度与重复开发成本。

## 架构概览

架构以 AI 模型开发训练平台为核心，向上支撑用户操作需求，向下依托底层算力与存储资源，通过 PA 平台复用公共能力，形成 “**用户层 \- 平台层（PA） \- 算力层（算力系统\+调度引擎\+K8S\+异构资源池）**” 的三层架构体系。

# 落地思考

基于 “循序渐进、用户导向、兼容过渡” 的原则，分期逐步推进云原生架构落地，兼顾业务连续性与技术升级效率。

## 一期：开发机容器化（关键入口场景落地）

### 核心目标

以开发机为切入点，完成容器化改造与基础能力搭建，降低算法工程师使用门槛，同时保障与原有Slurm集群的兼容过渡。

### 关键任务

1. 基于 K8S 实现开发机容器化部署，提供 Jupyterlab 标准化交互环境，预置主流框架与工具镜像，支持 pip/conda 依赖快速安装。

2. 保留算法工程师原有使用习惯，提供任务提交脚本，支持在容器化开发机中直接提交训练任务至现有Slurm集群，实现平滑过渡。

3. 完善开发机核心能力：资源规格灵活选择、多实例管理、协作共享、闲置自动回收、数据集挂载与代码版本控制。

## 二期：编排能力引入（训练流程标准化）

### 核心目标

引入流水线编排能力，简化训练流程复杂度，实现训练任务、镜像编译的标准化与复用，推进算力调度统一。

### 关键任务

1. 明确开发机与训练任务的职责边界：开发机仅用于代码开发与调试，不再承担训练任务提交与镜像编译工作，降低用户操作复杂度。

2. 搭建标准化训练流水线：封装 “代码拉取 \- 数据拉取 \- 参数配置 \- 训练执行 \- 镜像编译 \- 物料上传（归档）” 的可复用流程，提供流水线模板与可视化编排能力。

3. 统一算力资源调度：训练任务全部采用平台统一资源规格申请，依托`K8S+Volcano`实现算力调度，逐步替代原有Slurm集群的训练任务调度。
