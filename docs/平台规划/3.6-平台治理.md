# 3.6 平台治理

平台治理服务于训练平台自身的稳定运行、操作追溯和资源使用优化，不承担对外开放职责。训练任务、实验、故障恢复和内部工作流都在训练平台内闭环，不规划供第三方系统调用的开放接口、机器身份、服务账号或`Python SDK`。

本模块遵循以下边界：

|边界|规划口径|
|---|---|
|数据工程|数据获取、清洗、脱敏、质量、授权、版本和血缘由第三方数据工程系统负责；训练平台只保存就绪数据引用|
|角色权限|沿用算法工程师、`SRE`工程师和平台管理员三类现有角色及数据可见范围，不增加项目角色、对象级资源授权或临时权限|
|资源治理|统计并分析任务、团队和项目的资源容量与使用事实，不建设成本计费、复杂预算审批或新的资源授权模型|
|自动化|监控和建议只辅助用户决策，不自动取消任务、修改任务规格、调整队列或变更资源容量|

## 3.6.1 训练平台服务合并与功能回归

### 背景介绍

当前训练平台由`mlp-train-web`、`mlp-train-api`和`acs-server`三个服务组成。多服务部署、进程间通信、配置同步和版本协同增加了故障排查与日常维护成本，也使多人共同使用`AI`维护同一项目时需要理解多个运行单元，统一迭代和测试的效率较低。

### 建设目标

将三个服务合并为一个可独立启动、部署和观测的服务，保留现有页面调用接口、三类角色权限语义和核心用户流程；统一启动装配、配置、路由、鉴权、日志、监控、健康检查和发布流程。合并完成后，必须通过覆盖现有功能的回归测试，作为多人共同使用`AI`维护同一项目、共同迭代与测试的前置条件。

### 建议方案

合并只调整部署与进程边界，不重新划分业务模块职责。原有`Web`、`API`和`ACS`能力在单一服务内通过现有服务契约和显式依赖装配连接，禁止跨模块直接访问`DAO`、内部实体或私有运行时结构；发现循环依赖时优先提取稳定的模块接口或适配器，并说明新增抽象的变化点。统一服务入口负责配置加载、路由注册、鉴权中间件、日志与指标初始化以及健康检查，业务模块继续独立维护自身对象和生命周期。

回归验证至少覆盖：

1. 单服务启动、停止、健康检查、配置加载和发布回滚。
2. 原有`Web`页面与`API`路由、鉴权、权限拒绝和错误响应保持兼容。
3. 项目与用户管理、训练任务提交、取消、日志观测、实验入口及现有`ACS`能力保持可用。
4. 算法工程师、`SRE`工程师和平台管理员的菜单范围与数据可见范围保持不变。
5. 日志、指标和请求追踪能够在单服务内定位到具体业务模块和任务。

## 3.6.2 基础审计日志

### 背景介绍

任务取消、配置变更、运维处置或平台管理操作发生争议时，如果只保留最终状态，就无法还原谁在何时对什么对象执行了什么操作，也难以区分操作失败、系统异常和状态变化。

### 建设目标

记录训练平台内关键操作的操作者、现有角色、操作时间、来源、动作、对象、请求追踪标识、结果和失败原因摘要，支持按操作者、对象、动作、结果和时间范围检索，满足日常问题排查与责任追溯。

|记录内容|说明|
|---|---|
|操作主体|用户标识、显示名称和操作时的现有角色|
|操作上下文|操作时间、来源地址和请求追踪标识|
|操作对象|模块、对象类型、对象标识和必要的归属摘要|
|操作结果|动作、成功或失败结果及失败原因摘要|

### 建议方案

公共请求入口记录通用操作上下文，业务模块在关键状态变更完成后补充动作、对象和结果。审计记录只保存追溯所需的结构化摘要，不保存训练数据正文、数据预览、凭据、完整请求响应或外部数据工程系统的处理记录。查询范围复用现有三类角色与数据可见规则，不增加审计专属角色、项目级授权或复杂审批流程。

## 3.6.3 资源容量与使用统计

### 背景介绍

资源容量、任务申请量和实际使用量分散在调度与监控系统中时，算法人员难以判断单个任务是否申请合理，运维人员也难以比较不同团队和项目的容量占用、排队和利用趋势。

### 建设目标

统一展示任务、团队和项目在指定时间窗口内的资源容量、申请量、分配量、运行时长、利用率、排队和空闲情况，并明确统计口径、时间窗口和最近更新时间。

|统计维度|核心指标|主要用途|
|---|---|---|
|任务|申请与分配的`GPU/CPU/内存`、运行时长、利用率、排队时长和空闲时长|判断单任务资源规格是否合理|
|团队|关联队列可用容量、已分配量、任务数、利用率和排队趋势|识别团队容量压力和空闲资源|
|项目|任务资源使用量、峰值、平均利用率、排队和时间趋势|比较项目阶段投入与使用效率|

### 建议方案

从现有调度系统和监控系统只读汇总资源事实，按任务、团队、项目和时间窗口生成聚合快照。页面和报表读取聚合结果，不在列表中逐任务同步访问集群或监控系统；数据缺失或过期时显示证据范围和最近更新时间，不将缺失数据推断为零使用量。

## 3.6.4 资源使用监控

### 背景介绍

仅提供事后统计不能及时发现长时间空闲、持续低利用率、申请量与实际使用偏差或异常排队。运维人员需要从大量任务中识别真正值得关注的对象，并快速定位到所属团队和项目。

### 建设目标

基于明确的时间窗口和阈值，监控长时间空闲、持续低利用率、资源申请与实际使用显著偏离、异常排队和容量逼近上限等情况，并关联对应任务、团队与项目。

### 建议方案

监控规则读取资源聚合快照，生成包含对象、规则、阈值、观测值、统计窗口和数据新鲜度的异常记录。规则状态使用固定命名类型并保留调整记录；监控仅提示和通知现有角色，不直接修改任务、队列或容量。底层监控数据不可用时保留最近一次有效结论并明确标记过期，不持续生成重复异常。

## 3.6.5 资源优化建议

### 背景介绍

发现资源异常后，如果只给出“利用率低”之类的结论，算法人员仍然需要自行判断是任务规格过大、数据读取受限、训练停滞还是排队配置不合理。建议需要提供可核对的证据和预期影响，才能辅助用户采取行动。

### 建设目标

针对任务、团队和项目生成可解释的资源优化建议，说明触发规则、观测证据、统计窗口、建议动作和预期影响，帮助用户评估缩减任务规格、结束空闲任务、调整提交时间或优化训练配置等措施。

### 建议方案

首期只使用可回放的确定性规则，不引入自动决策模型。建议与原始资源快照和监控异常关联，允许用户标记已处理、不适用或稍后关注，以便校准阈值和规则；平台不根据建议自动取消任务、修改任务规格、调整队列或变更资源容量。列表使用预聚合摘要，详情按需读取证据，避免逐项远程查询。
