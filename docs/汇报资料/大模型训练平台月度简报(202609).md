# 大模型训练平台月度简报(202609)

# 第一部分：核心方向进展大盘（看现状）

## 项目背景

原有大模型训练系统采用开源方案，能够支持短时训练任务，但在大规模预训练等长周期任务中稳定性不足；同时，开源社区活跃度有限，故障处置较多依赖运维人员手动排查，定位与恢复效率较低。2025年12月至2026年8月，`AIHPC`集群累计记录`111`起故障，其中`GPU`硬件故障`82`起，占`73.88%`，`IB`网络故障`13`起，占`11.71%`，且2026年7月至8月故障量明显处于高位。随着训练任务规模扩大、运行周期延长，亟需建设面向长周期训练的稳定调度、统一可观测和故障闭环能力。

## 核心目标、交付进展与资源投入

**核心目标**：总体目标是提高大模型长周期训练的稳定性，缩短训练中断与排障时间，并降低平台长期维护成本。第三季度聚焦建设`MVP`版本，优先解决长周期训练稳定性不足、运行状态缺少统一观测、故障依赖人工排查等核心痛点，并在`SLM`项目中进行小规模投产验证。

|**重点方向**|**本季度交付**|**阶段价值**|**状态**|
|---|---|---|---|
|**训推一体与训练管理**|落地`K8S + Volcano`训练链路，打通任务、队列、配置、日志和告警|训推复用基线、调度、监控和运维体系，避免双技术栈重复建设|一期完成，真实集群验证中|
|**可观测数据中心与故障保障**|完成统一可观测数据中心一期建设，按训练任务关联指标、日志、事件和`FastX`告警，形成故障节点隔离、修复和重新入池闭环|从分散排查转为任务级全链路分析，提升定位和协同处置效率|一期完成，持续优化真实样本|
|**平台治理**|完成用户、团队、角色、集群、节点和队列管理|为资源配额、优先级、审计和利用率分析建立基础|基础能力完成|

**资源投入**：Q3投入`3`名研发和`1`名测试，郭强担任项目及研发主要负责人，薛童协同`AI-HPC`故障分析和保障机制；后续保持`3`名研发持续迭代维护。上线初期复用`SLM`已有`16`台`H200`服务器及配套`IB`网络，无需新增硬件采购。

## 核心能力与价值看板

本季度已完成训推一体云原生底座、统一可观测数据中心和训练故障归因能力的一期建设，形成任务提交、运行监控、故障定位和资源恢复闭环。训练与推理采用了统一的技术底座，降低长期技术复杂度和维护成本；建设完成可观测数据中心，统一汇聚指标、日志、事件并接入告警，支撑任务级全链路监控与分析，提高故障发现的全面性和定位效率。

# 第三部分：核心策略与具体行动计划（谋出路）

## 下阶段重点工作安排

下阶段将围绕算法研发提效、训练稳定性提升和运维智能化三条主线推进以下工作。其中，后训练编排当前业务规模较小，作为后置储备方向。

|**工作项**|**背景与必要性**|**价值**|**计划完成时间**|
|---|---|---|---|
|**实验管理与分析闭环**：关联实验、`Run`与任务，归集配置、指标和产物，支持`TensorBoard`及`Run`对比|实验配置、指标和产物分散，对比与复现依赖人工整理|缩短实验筛选与复盘周期，提高结果复现和经验复用效率|2026.10|
|**作业内快速恢复能力**：建设作业级原地重启能力，对可恢复故障保留现有作业资源并从最近断点续训；进一步建设进程内恢复能力，减少容器和`Python`进程重建开销|训练`Hang`或局部进程异常常导致整作业退出，从头调度和重新申请节点耗时，容易造成数小时算力和训练进度损失|避免可恢复故障触发整作业重排队，降低恢复时长和无人值守期间的算力闲置|2026.11|
|**高效断点保存与续训**：建设异步`Checkpoint`与本地分层保存能力，由后台进程写入断点，并完善断点完整性校验和可恢复点管理|传统同步`Checkpoint`写盘时，全部训练进程需停下等待；大模型断点体量大、写盘可持续数分钟，造成`GPU`空转和共享存储`IO`压力|将断点开销从训练主链路剥离，降低算力等待和共享存储峰值压力，减少故障后的进度回退|2026.11|
|**慢节点与性能劣化检测**：建设慢`Rank`检测能力，持续监测各`Rank`的`GPU`和`CPU`性能，输出慢`Rank`与疑似节点报告，并结合真实样本校准检测阈值|大规模同步训练中，个别`GPU`或节点性能下降会拖慢全部`Rank`，集群整体吞吐下降却难以定位责任节点|尽早发现隐性性能损失，避免单个慢节点长时间浪费整作业算力，提高集群有效吞吐|2026.12|
|**故障归因与健康诊断**：建设系统健康检查能力，结合`NVML`硬件健康数据、分布式日志聚合和已有指标、事件，形成带完整上下文的故障报告和版本化规则库|训练崩溃后，`GPU`硬件、`NVLink`、`NIC`网络与软件异常的表现容易混淆，证据分散导致排查和误重试成本高|缩短故障发现与定位时间，减少无效重试和人工跨系统排查，支撑故障节点精准隔离|2026.12|
|**容错组件标准化接入**：建设模块化容错`API`和统一容错启动器，在官方训练模板中为`DDP`、`PyTorch Lightning`等训练代码提供低侵入接入与统一配置|`PyTorch`原生分布式容错能力有限，算法团队自行实现`Hang`检测、快速重启和高效断点工作量大，且多套实现难以统一治理|将通用容错能力下沉到平台，缩短算法接入周期，避免重复开发并降低长期维护成本|2026.12|
|**开发机标准化管理**：统一镜像、规格、路径、权限和生命周期，支持一键转训练及空闲回收|开发与训练环境不一致，且空闲开发机容易长期占用资源|降低环境漂移导致的失败，减少环境准备时间并提高`GPU`利用率|2027 Q1|
|**后训练编排系统优化**：优先梳理流程和基础规范，保留模板与编排扩展能力，根据业务增长逐步建设|当前业务规模较小，短期对完整编排能力的需求有限|控制当期投入并避免过早建设，为后续业务扩展保留基础|待定|
|**`AI Native`智能化运维升级**：引入`AI Agent`聚合故障证据并生成排查建议，高风险动作保留人工确认和审计|告警、指标、日志和事件分散，人工关联证据难以支撑规模化运维|缩短告警理解和初步定位时间，推动运维知识沉淀与智能辅助处置|待定|
